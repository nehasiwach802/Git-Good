# Circuitly JSON API contract - v1

Status: finalized contract, explicitly confirmed by the project owner on 1 November 2026.
Decision: "the api contract given above is the finalized api contract".
Android and backend implementation must follow this document and openapi.json.
Changes require an explicit contract revision; deployment is not a reason to silently
change endpoint paths, payloads, event semantics or version checks.
This is documentation, not a deployment or an Android integration.
The existing Render dummy service had only `/health` and `/api/sessions` for upload
connectivity. It does not implement this v1 contract. Its Android integration has
been removed. The previously generated integration PDFs describe historical code.

Machine-readable specification: `openapi.json` (OpenAPI 3.1).
Schema-checked illustrative payloads: `examples.json`.
This document defines the lifecycle/concurrency semantics that JSON Schema alone
cannot enforce. Implementers must follow both the schemas and these rules.

## 1. Versioning, authentication and response envelope

Target base URL: `https://git-good-1.onrender.com/api/v1`.
All operations except health require:

```
Authorization: Bearer <Firebase ID token>
Accept: application/json
```

Backend verifies the token, derives the owner UID, and checks session ownership on
every session operation. Client-supplied owner IDs are not accepted. Requests for
another user's session return 404 to avoid disclosing its existence. Expired or
missing tokens return 401; Android refreshes the token before an explicit retry.
TLS is required. The v1 prefix is a future target, not an existing endpoint claim.

All successful domain responses use:

```json
{"request_id":"<UUID>","data":{}}
```

Errors use the error envelope in section 8. Health is the one public endpoint with
its own simple response. Timestamps are RFC 3339 UTC. IDs generated by the service,
event IDs and idempotency keys are UUIDs. Session/revision versions are positive
integers. IDs and versions must not be inferred from human display names.

`mode` in every session is `stub` or `live`. A stub session must have
`assessment: null`; it must never emit a simulated correct/incorrect verdict.
Android labels stub sessions clearly. A live model must be allowed to return
`inconclusive`, rather than guessing correctness.

## 2. Endpoints

| Method and path, relative to base | Input | Successful result |
| --- | --- | --- |
| GET /health | No auth | 200: health + API version + stub/live mode |
| GET /experiments | Firebase token | 200: experiment list with exact IDs, versions, support and capabilities |
| POST /sessions | JSON experiment_id + experiment_version; Idempotency-Key | 201: new SessionResponse |
| POST /sessions/{session_id}/images | Multipart image + description + expected_session_version; Idempotency-Key | 202: image accepted, user message added, extraction job queued; SessionResponse |
| GET /sessions/{session_id} | Firebase token | 200: complete authoritative SessionResponse |
| POST /sessions/{session_id}/events | JSON Event | 200 for immediate updates, 202 for queued work; SessionResponse |

No separate chat-message endpoint, close endpoint or image-retention promise is
implied by the old dummy API. They are implemented through v1 only as defined here.
No WebSocket/SSE is required in v1; Android polls while a job is active.

## 3. Experiment catalog

The first catalog uses these exact ID/name pairs and experiment_version `"1"`:

| ID | Name |
| --- | --- |
| not-gate-7400 | NOT Gate Using IC 7400 NAND Gates |
| ohms-law | Verification of Ohm’s Law |
| rc-low-pass-filter | RC Low-Pass Filter |
| inverting-op-amp | Inverting Op-Amp Amplifier |
| half-wave-rectifier | Half-Wave Rectifier |

An experiment includes `id`, `name`, `version`, `description`, `support_status`,
`support_reason` and boolean capabilities: `image_analysis`, `follow_up_images`,
`measurements`, `instructor_help`. Support status is `available`, `coming_soon` or
`unavailable`. Only available entries can start sessions. The backend reports
actual support; listing these names does not claim the model supports all five.
Historical sessions remain pinned to the version used when they were created.
A changed experiment definition requires a new version. An unsupported requested
version returns 409 EXPERIMENT_VERSION_UNAVAILABLE, never silent substitution.

## 4. Session creation and image upload

Create once when the user taps Continue on Home, not merely when selecting an
experiment. Persist the idempotency key until the outcome is known.

```json
{"experiment_id":"ohms-law","experiment_version":"1"}
```

The new session starts at session_version 1, status `awaiting_image`, with no job,
candidate or assessment. Its pending_actions contains a typed `upload_image`
action. Android stores the returned session_id, then uploads the selected image.
If image upload fails, retry against the same session rather than creating another.

Image request uses `multipart/form-data` with exactly:

- `image`: JPEG or PNG, 1 to 5,242,880 bytes (5 MiB), verified from actual content.
- `description`: nonblank text, 1-2000 Unicode characters after trimming edges.
- `expected_session_version`: last snapshot version, as an integer form field.

The backend validates all fields before accepting any persistent mutation. It
returns an image receipt: image_id, content_type, size_bytes, width, height, sha256.
Accepted upload atomically appends one user message containing the description
and image attachment, increments session_version, invalidates the old candidate,
assessment and candidate-specific actions, and queues extraction. It returns 202;
that means accepted, not circuit analysis completed.

New images are permitted in an open idle session if follow_up_images is true.
The extraction revision counter is monotonic within the session: invalidating a
candidate must never reuse an older revision number.

Image URLs in messages are read-only, short-lived signed HTTPS URLs with an
explicit url_expires_at. Refresh the session when a URL expires. Do not place
Firebase tokens in image URLs. Data deletion/retention policy must be published by
the service separately; closing a session is not an image-deletion operation.

## 5. Authoritative session snapshot

Each snapshot contains:

- session_id, mode, experiment_id, experiment_version, session_version.
- status, created_at, updated_at.
- messages: complete ordered history, stable message IDs, user/assistant/system role,
  text, attachments, and timestamps. Android replaces/merges by message ID, never
  appends the same full snapshot again as new messages.
- candidate: null, or revision, source image_id, components, connections, confirmed.
  Components have stable IDs and named pins; connections refer to those IDs/pins.
- pending_actions: only currently actionable typed controls.
- job: null, or queued/running extraction, analysis or reply job with retry_after_ms.
- assessment: null, or verdict, explanation, findings and the exact candidate_revision.

Every externally observable change (new message, action, candidate, job status or
assessment) atomically increments session_version. GET alone does not increment
it. Backend uses compare-and-swap/transactional validation to serialize mutations.
A replay of an already accepted operation does not increment it again.

Session statuses:

| Status | Meaning |
| --- | --- |
| awaiting_image | New session needs its first image |
| extracting | Image accepted; extraction queued/running |
| awaiting_input | User must review/confirm wiring or supply requested evidence |
| analyzing | Model analysis or conversational reply queued/running |
| ready | No job or mandatory action blocks a follow-up |
| failed | A job failed; explicit retry or replacement evidence may be offered |
| closed | Conversation ended; read-only |

Extraction that cannot produce usable wiring returns awaiting_input with an
upload_image action and an explanatory assistant message. It must not invent a
candidate. A usable extraction requires explicit user confirmation of its revision
before a correctness assessment. Confirmation marks that revision confirmed and
queues analysis. Corrections always create a new unconfirmed revision.

An assessment is valid only for the current confirmed candidate revision. It has
verdict `correct`, `incorrect` or `inconclusive`, explanation, and structured
findings with component/connection IDs. A later image/correction clears it. A
reply that changes the candidate must also invalidate its prior assessment.

V1 restoration returns full history without pagination. Backend must not silently
truncate messages. Future pagination requires a documented contract extension.
Android saves session_id and restores with GET after app restart, not by recreating
user messages from text cached on the device.

## 6. Typed events and actions

Every event has:

```json
{
  "event_id": "00000000-0000-4000-8000-000000000007",
  "expected_session_version": 8,
  "type": "confirm_candidate",
  "candidate_revision": 3,
  "payload": {
    "action_id": "00000000-0000-4000-8000-000000000005"
  }
}
```

`candidate_revision` is required for candidate-specific events and omitted for
ordinary message, retry, close and instructor events. Each event has a distinct
payload schema (discriminated by type); arbitrary extra fields are rejected.

| Event type | Payload | HTTP behavior |
| --- | --- | --- |
| message | text, 1-4000 nonblank characters | 202; queues conversational reply |
| confirm_candidate | action_id | 202; confirms exact revision, consumes its review/confirmation actions, queues analysis |
| submit_correction | action_id, connection_changes, optional note | 200; apply validated add/remove/replace connection changes atomically, create new unconfirmed revision, require re-review |
| submit_measurement | action_id, measurement_id, finite numeric value, exact unit | 202; validate against requested field, record user evidence and queue analysis |
| submit_check_result | action_id, check_id, passed/failed/inconclusive, optional observation | 202; record user-reported evidence and queue analysis |
| request_instructor_help | action_id, reason | 200; record request only when actual backend help integration is enabled |
| retry_job | action_id, failed_job_id | 202; queue one replacement job for the failed operation |
| close_session | reason: user_exit | 200; close session and clear pending actions |

Candidate confirmation, measurements and check events must refer to a still-pending
action_id belonging to this session/revision. Measurement units and allowed ranges
come from the action, not from Android guesses. Measurements and check results are
user-reported evidence, not trusted statements that the circuit is correct.

Pending action types are:

- upload_image: prompt, accepted_content_types, max_size_bytes, description_required.
- review_connection: connection_id, prompt, exact candidate_revision.
- confirm_revision: prompt, exact candidate_revision.
- enter_measurement: measurement_id, quantity, unit, nullable min/max, probe_points,
  exact candidate_revision.
- perform_check: check_id, instructions, exact candidate_revision.
- request_instructor_help: reason; only emitted if human-help integration is available.
- retry_job: failed_job_id and reason.

All actions have action_id, label, type and nullable candidate_revision (required
non-null where relevant). Android renders these schemas as buttons/forms and must
never infer controls from conversational text. It must not report instructor help
as delivered merely because a message mentioned it; backend acknowledgment must
accurately describe what was recorded/queued. Unknown future action types must
show an unsupported-action fallback, not a guessed button.

## 7. Retries, concurrency and polling

Create/image operations require `Idempotency-Key: <UUID>`. Deduplication is scoped
to authenticated UID + operation path + key for at least 24 hours. Compare a
canonical fingerprint of validated inputs; for images use image SHA-256 plus
fields, not the random multipart boundary. Same key/same input replays the original
status/body and sets `Idempotency-Replayed: true`. Same key/different input returns
409 IDEMPOTENCY_CONFLICT. Do not automatically retry after the deduplication window
without reconciling session state.

Events deduplicate by authenticated UID + session_id + event_id for the retained
session lifetime. A duplicate event replays its original outcome. Deduplicate
before version checking; otherwise a successful event retried after a timeout
would be mistaken for a stale new event. Retrying an uncertain request keeps the
original key/event ID and payload. A genuinely new user operation uses a new ID.
A replay can contain an older snapshot; never replace a newer client snapshot
with it. GET the current session when needed.

For new events/uploads, verify ownership, open state, current revision/action and
expected_session_version before mutation. Wrong revision is 409 STALE_CANDIDATE;
otherwise a wrong session version is 409 STALE_SESSION. Both return the latest
snapshot in error.current_session. Android refreshes and asks the user to review
again; never silently resubmit a confirmation for newer wiring.

Only one model job may run per session in v1. During a job, other new messages,
images, corrections, measurements and confirmations return 409 JOB_IN_PROGRESS.
GET, replayed operations and close_session remain allowed. A worker must check
that its session is open and that its input revision is still current before
committing results, so old jobs cannot overwrite new/closed state.

Android polls GET /sessions/{id} while job is non-null, using job.retry_after_ms
(default backend recommendation: 2000ms). Pause polling in background and fetch
on resume. Network failures back off to at most 30s between attempts. Respect
Retry-After for 429/503. A null job means stop polling; it does not imply a correct
circuit. Render status, assessment and pending_actions from the snapshot.

Failed jobs expose status=failed, an honest assistant/system error message and a
retry_job action when retry is possible. Replaying the original successful upload
does not rerun a failed job; use the typed retry_job event.

## 8. Error envelope

```json
{
  "request_id": "00000000-0000-4000-8000-000000000012",
  "error": {
    "code": "STALE_CANDIDATE",
    "message": "Wiring changed. Review the current revision before confirming.",
    "retryable": false,
    "field_errors": [],
    "current_session": null
  }
}
```

For actual stale errors current_session must contain the authoritative snapshot;
null above only illustrates the field shape. See examples.json for the complete
stale-response example. Do not include session snapshots in unauthorized errors.

| HTTP | Codes / required client response |
| --- | --- |
| 401 | UNAUTHENTICATED; refresh Firebase token |
| 403 | FORBIDDEN; do not escalate privileges |
| 404 | NOT_FOUND; unavailable/unowned resource |
| 409 | EXPERIMENT_UNAVAILABLE, EXPERIMENT_VERSION_UNAVAILABLE, STALE_SESSION, STALE_CANDIDATE, ACTION_UNAVAILABLE, SESSION_CLOSED, JOB_IN_PROGRESS, IDEMPOTENCY_CONFLICT |
| 413 | IMAGE_TOO_LARGE; select a smaller image |
| 415 | UNSUPPORTED_IMAGE; supply JPEG/PNG |
| 422 | VALIDATION_ERROR; render field_errors |
| 429 | RATE_LIMITED; honor Retry-After |
| 503 | SERVICE_UNAVAILABLE; honor Retry-After |
| 500 | INTERNAL_ERROR; readable error, no stack traces |

retryable indicates whether the exact same uncertain operation can be retried
without changing meaning. It is false for revision/validation conflicts. A
JOB_IN_PROGRESS response may be retryable after refreshing current_session.
All rejected validation/conflict requests leave domain state unchanged.

## 9. Exit conversation

Visible Exit sends a retry-safe close_session event against the last version.
Backend immediately marks closed, clears actions, cancels pending work where
possible, and prevents any late worker result from being committed. Closed
sessions remain GET-readable subject to ownership/retention; other new mutations
return SESSION_CLOSED. A fresh close event against an already closed session
returns the closed snapshot without another version increment.

Android can return Home immediately and retain a queued close event if offline;
show that closure is pending rather than claiming it reached the backend.
Clear Home image/description but retain experiment selection. After closure,
Continue starts a new session. Closing is not deleting account/session history.
For a stale close, GET and issue a new close event using the current version;
closing does not confirm any circuit revision. For stale confirmations, user
re-review is mandatory instead.

## 10. Rollout boundary

The app is restored to its pre-dummy-integration flow: authentication -> experiment
selection -> Home with photo picker/camera, preview and description. Continue has
no network action. This finalized contract does not change that runtime behavior.
Next work, only after approval: backend implements v1, then Android repository and
conversation UI integrate it. Do not repoint the old dummy upload client at these
routes; request/response semantics differ.
